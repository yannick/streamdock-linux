# ADR-001: Architecture and libraries of streamdockd

- Status: accepted (stack chosen by the maintainer in the H15-3 decisions, 2026-10-17)
- Deciders: the maintainer (product), the lead agent
- Issues: H15-3 (project setup), H15-4 (this scaffold)

## Context

We are writing Linux software for the StreamDock 293s (FHOOU / Mirabox, USB `6603:1003`).
Reverse engineering (H15-2, H15-9) shows it is the **N3 / Ajazz AKP03 family**: 6 LCD keys (3×2),
3 plain buttons and 3 knobs (turn + press).

The product, from H15-3:

- A **Rust daemon** that configures and drives the dock, similar to OpenDeck. Its purpose is to let
  the dock control Home Assistant, KNX and other devices, and to display their status on the keys.
- A **web UI written in TypeScript, compiled into the binary**, in a cyberpunk style, that shows
  every key press and knob interaction live.
- **All UI APIs send binary protobuf** over connectRPC, and **every UI update is pushed** to every
  connected client in real time.
- Built with **proa** (<https://proa.so>).

## Decision

### Shape

```
┌──────────────────────────── streamdockd (one binary) ────────────────────────────┐
│ device manager ── streamdock-hid ──hidraw──▶ dock (6603:1003)                    │
│       │ events / commands                                                        │
│  event bus (tokio broadcast) ──▶ integrations (Home Assistant, KNX, … later)     │
│       │                                                                          │
│  axum 0.8 router                                                                 │
│   ├─ /                 proa-rendered shell (theme, layout, SSR fallbacks)        │
│   ├─ /static/*         React islands + self-hosted React, embedded (include_dir) │
│   └─ /streamdock.v1.*  connectrpc services, binary protobuf; WatchEvents streams │
└──────────────────────────────────────────────────────────────────────────────────┘
browser: proa bootstrap mounts React/TS islands ─ connect-web (binary) ─▶ WatchEvents
```

Workspace crates:

| Crate | Role |
|---|---|
| `build-info` | Build-time git identity and UTC timestamp (H15-77), isolated so Rust edits update the version without rebuilding the web UI; no dependencies. |
| `streamdock-hid` | Device driver: discovery, init, input events, brightness, key images (H15-5). |
| `streamdock-proto` | Generated protobuf types and Connect service stubs for `proto/streamdock/v1` (H15-6). |
| `slimproto` | Lyrion's player protocol (Slimproto), client side: discovery, connection, commands, stream fetch; the `Playback` trait is the interface to decode + output (H15-55, H15-47). |
| `player` | The built-in player's audio side: `decode` (stream → interleaved `f32` frames into a `FrameSink`, H15-56) and `output` (PipeWire, the `Playback` impl, H15-47). |
| `wakeword` | Wake word detection (H15-68): the TFLite Micro audio frontend, an int8 streaming interpreter for microWakeWord models and the detector; pure Rust, no dependencies but `thiserror`. |
| `streamdockd` | The daemon: device manager (H15-8), event bus, Connect API (H15-6), web UI (H15-7). |

### Web layer (option A of the H15-3 decision)

- **proa renders the page shell server-side**: layout, theme, and each island's static fallback.
  We use proa's rendering crates (`proa_core`, `proa_macros`'s `html_sync!`) and `proa_react`'s
  island helpers (`react_island`, `render_import_map_entries`, `react_bootstrap`) directly on our
  own axum router.
- **The live UI is React + TypeScript islands** in `web/`, built with Vite into ES modules.
  proa's bootstrap mounts them with `createRoot` (client render, not hydration: the islands
  replace the static fallback with live data).
- **React is self-hosted.** proa's default import map loads React from the esm.sh CDN. The daemon
  must work offline, so `web/` builds `vendor/react.js`, `vendor/react-jsx-runtime.js` and
  `vendor/react-dom-client.js` as entries of the same Vite build as the islands. The page's import
  map points the bare specifiers at them, so the bootstrap and all islands share one React
  instance.
- **Embedding:** `crates/streamdockd/build.rs` runs `pnpm install` / `pnpm build` in `web/`, and
  `include_dir!` embeds `web/dist/` in the binary. No files are served from disk at runtime.

### API

- `proto/streamdock/v1/*.proto` is the single source of truth, linted with `buf`.
- **connectrpc (connect-rust)** serves it from the axum router as a Tower service, with the Connect
  protocol and binary protobuf. Live data uses server-streaming RPCs (`DeviceService.WatchEvents`)
  fed by a tokio broadcast channel, so every client gets every event and a slow client cannot block
  the others.
- The browser uses `@connectrpc/connect-web` with `useBinaryFormat: true` and `@bufbuild/protobuf`
  types generated by `buf generate` into `web/src/gen/`.

## Consequences

- One self-contained binary; the UI works without internet access.
- **proa is young (0.3).** Its axum adapter, `proa_framework_axum` 0.3, is built on **axum 0.7**,
  while connectrpc's axum integration needs **axum 0.8**. We therefore don't use
  `proa_framework_axum` (routing, `FrameworkBuilder`, `EmbeddedStaticService`). We use proa's
  rendering and island crates on our own axum 0.8 router, with a small embedded static-asset
  handler (`crates/streamdockd/src/web.rs`). Revisit when proa's adapter moves to axum 0.8.
- The React islands are plain TypeScript talking to the Connect API. If proa ever becomes a burden,
  dropping the shell and serving the islands as an SPA (option B) is a small change.
- Building `streamdockd` needs Node + pnpm. `STREAMDOCKD_SKIP_WEB_BUILD=1` skips the web build for
  Rust-only work.
- The proto files are the API contract between `streamdockd` and the UI. Breaking changes need
  `buf breaking` to pass, or a new package version (`streamdock.v2`).

## Alternatives considered

| Alternative | Why not |
|---|---|
| B: plain axum + embedded React SPA, no proa | Simplest, but drops proa (an H15-3 requirement). Remains the fallback. |
| C: `tonic` + `tonic-web` + React SPA | Mature, but gRPC-Web on the wire instead of Connect; two protocols for no gain. |
| `connectrpc-axum` 0.2 (community, prost-based) | Fallback if we ever need the prost ecosystem; connect-rust is official and passes the conformance suite. |
| proa-native UI (rsjs islands in Rust) | Contradicts the TypeScript UI requirement; rsjs is young. |
| `ssr_rs` (React SSR in embedded V8) | Real React SSR, but V8 in the binary is heavy; not needed for a LAN dashboard. |
| Leptos, Dioxus | Mature full-stack Rust, but the UI would be written in Rust, not TypeScript/React. |
| `rspc` (tRPC-style) | JSON, not binary protobuf. |
| `proa_framework_axum` as the router | axum 0.7, conflicts with connectrpc's axum 0.8 (see Consequences). |
